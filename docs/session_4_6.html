Session 4.6

Cybersecurity in Automotive

The Regulatory Landscape: UNECE WP.29 & ISO/SAE 21434

Historically, automotive engineering prioritized physical safety (brakes, crash structures) over digital security. This changed dramatically with the introduction of the UNECE WP.29 R155 regulation. It mandates that all new vehicles must have a certified Cybersecurity Management System (CSMS) to be legally sold in major global markets.

To comply with this regulation, the automotive industry adopted the ISO/SAE 21434 standard, which enforces "Cybersecurity Engineering" throughout the entire lifecycle of a vehicle—from concept to decommissioning.

Why C/C++ Fails ISO/SAE 21434

A core tenet of ISO 21434 is "Security by Design". Relying on languages with undefined behavior (like C and C++) directly contradicts this principle when memory-safe alternatives exist. A single buffer overflow in a Telematics Control Unit (TCU) can compromise the entire vehicle network.

Breaking News: Industry Trends in Auto Cybersecurity

Automotive security is shifting from compliance-driven paperwork to hardcore engineering. OEMs are realizing that the only mathematical way to satisfy R155's "Secure by Design" mandate is memory-safe architecture.

AUTOSAR Formally Adopts Rust

The AUTOSAR consortium, which defines standard software architecture for automotive ECUs, has officially formed a working group to integrate Rust. This represents the death knell for new C/C++ development in highly critical vehicle components.

Zero-Day Bug Bounties

Following massive Pwn2Own automotive hacking events where Tesla and others were breached via Bluetooth/Wi-Fi memory exploits, manufacturers are deploying Rust-based parser replacements to physically impossible-to-hack standard zero-day vectors.

CISA Urges Auto Migration

The US Cybersecurity and Infrastructure Security Agency (CISA) has explicitly called out connected vehicles as critical infrastructure. They strongly advise the automotive supply chain to migrate away from C/C++ to eliminate memory safety vulnerabilities at the source.

The Modern Automotive Threat Landscape

Modern vehicles have a massive attack surface. Hackers no longer need physical access to compromise a car.

  • Telematics & OTA (Over-The-Air): Remote code execution (RCE) via malicious cellular packets.
  • Infotainment & Bluetooth: Buffer overflows in the Bluetooth stack allowing attackers to pivot into the internal vehicle network.
  • Keyless Entry (RF/NFC): Relay attacks that spoof the physical proximity of the owner's key fob.
  • CAN Bus Injection: Once inside the network, injecting fake CAN frames to manipulate steering, braking, or engine parameters.

How Rust Defends the Vehicle

By writing edge-facing components (like the TCU and Infotainment parsers) in Rust, automotive engineers can categorically eliminate memory safety vulnerabilities.

Securing OTA Updates

If an OTA update parser in C is compromised, the attacker gains persistence. In Rust, strict bounds checking and memory safety prevent the payload from overflowing the buffer.

fn parse_ota_firmware(payload: &[u8]) -> Result<Firmware, Error> {
    // Rust guarantees that we cannot read past the end of the payload slice
    if payload.len() < 1024 {
        return Err(Error::InvalidHeaderSize);
    }
    
    // Safely extract the cryptographic signature without pointer arithmetic risks
    let signature = &payload[0..256]; 
    verify_crypto_signature(signature)?;
    
    Ok(Firmware::new(&payload[256..]))
}
