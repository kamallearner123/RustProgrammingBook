Session 1.2

Data Sharing and Threads

The Danger of Concurrency

Modern processors have many cores. To maximize performance, we use multithreading. However, when multiple threads run simultaneously and share the same memory, they can easily step on each other's toes.

If Thread A and Thread B both attempt to read and write to the same variable at the exact same moment without coordination, the data becomes corrupted. This is called a Data Race.

sequenceDiagram participant TA as Thread A participant M as Shared Memory (Balance: 1000) participant TB as Thread B TA->>M: READ Balance (Gets 1000) TB->>M: READ Balance (Gets 1000) TA->>TA: Calculate Add 1 (1001) TB->>TB: Calculate Add 1 (1001) TA->>M: WRITE Balance (Sets 1001) TB->>M: WRITE Balance (Sets 1001) Note over TA,TB: Both increments executed,
but the final total is 1001 instead of 1002!
This is a Data Race.

A Classic C Data Race

In C/C++, there is nothing preventing you from causing a data race. The compiler will happily compile the code below, and the bug will only show up occasionally at runtime (making it notoriously hard to debug).

#include <stdio.h>
#include <pthread.h>

// Shared global data
int account_balance = 1000;

void* process_transaction(void* arg) {
    // Both threads try to modify the balance simultaneously
    for(int i = 0; i < 100000; i++) {
        // This is NOT an atomic operation!
        // It consists of: READ, MODIFY, WRITE
        account_balance = account_balance + 1; 
    }
    return NULL;
}

int main() {
    pthread_t thread1, thread2;

    // Start two threads that share the account_balance
    pthread_create(&thread1, NULL, process_transaction, NULL);
    pthread_create(&thread2, NULL, process_transaction, NULL);

    // Wait for both to finish
    pthread_join(thread1, NULL);
    pthread_join(thread2, NULL);

    // We expect 1000 + 100000 + 100000 = 201000
    printf("Final Balance: %d\n", account_balance);
    
    return 0;
}

The Result

If you run this code, the output will almost never be 201000. It might be 145293, or 198302. The operations overlap.

Why this is a Security Vulnerability: Data races in critical logic (like checking if a user is authenticated, or validating a bank transfer) can allow attackers to bypass security checks entirely by exploiting the tiny timing window between a thread reading a value and acting on it (known as a Time-of-Check to Time-of-Use or TOCTOU vulnerability).

The Solution?

In C/C++, the developer must remember to use Mutexes (Mutual Exclusion locks) or semaphores to manually block other threads while reading/writing. Forgetting to lock, locking in the wrong order (Deadlocks), or forgetting to unlock will instantly break the application.

As we'll see later, Rust prevents data races entirely at compile time. If your Rust code compiles, data races are mathematically impossible.
