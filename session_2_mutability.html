Session 2.6

Mutable vs Immutable References

The Golden Rule of References

Rust prevents data races at compile time using one simple, unbreakable rule regarding references.

At any given time, you can have either:
  • One mutable reference (&mut T)
  • OR any number of immutable references (&T)
But you cannot have both at the same time.

Example 1: Multiple Immutable References

View C/C++ Buggy Code 

// C Mutable Aliasing / Data Race
void process_transaction(int *sender_bal, int *receiver_bal) {
    // If sender_bal and receiver_bal point to the EXACT same memory address
    // (aliasing), the logic breaks entirely.
    *sender_bal -= 100;
    *receiver_bal += 100;
}
                        
fn main() {
    let s = String::from("hello");

    let r1 = &s;
    let r2 = &s;
    let r3 = &s;

    println!("{} and {} and {}", r1, r2, r3);
}

Why: You can have as many immutable references as you want. Since nobody is modifying the data, it's perfectly safe for any number of references to read it simultaneously.

Example 2: Error - Mixing Mutable and Immutable

fn main() {
    let mut s = String::from("hello");

    let r1 = &s; // no problem
    let r2 = &s; // no problem
    let r3 = &mut s; // BIG PROBLEM

    println!("{}, {}, and {}", r1, r2, r3);
}

Error Explanation: cannot borrow `s` as mutable because it is also borrowed as immutable. If r3 modifies the string, the data that r1 and r2 are pointing to could change or be relocated in memory without them knowing. This causes crashes. Rust prevents this at compile time.

Example 3: Non-Overlapping Scopes

fn main() {
    let mut s = String::from("hello");

    let r1 = &s;
    let r2 = &s;
    println!("{} and {}", r1, r2);
    // r1 and r2 are no longer used after this point

    let r3 = &mut s; // This is now okay!
    r3.push_str(" world");
    println!("{}", r3);
}

Output:

hello and hello
hello world

Why: A reference’s scope ends the last time it is used. Because r1 and r2 are never used after the first println!, their scope is over. Therefore, creating a mutable reference r3 afterward does not violate the rule.

Knowledge Check (MCQ)

Question: Why does Rust prohibit having a mutable reference and an immutable reference active at the same time?

  1. To save memory allocation overhead.
  2. To enforce a functional programming paradigm.
  3. To prevent data races and dangling pointers while reading.
  4. Because the compiler cannot infer the types.

Answer: C. If data is modified via a mutable reference while being read via an immutable reference, it causes data races and memory corruption.
